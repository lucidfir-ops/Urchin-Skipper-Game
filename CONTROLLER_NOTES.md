# Controller behavior and remaining physical checks

Updated September 14, 2026. USB Xbox is the designer-confirmed physical baseline. The game has device-specific mappings and active-input prompts; built-in Steam Deck controls and desktop paddles still need physical verification. [Current default control design](docs/CONTROL_DESIGN.md) supersedes older action descriptions below: Y deploys/boards, X handles bags, A recalls nearby bubbles, R3 opens assists, B opens orders. RB cycles the permitted difficulty presets and retains custom widget slots. Left-stick throttle changes and lateral thrust cannot engage together. Explicitly remapped controls remain protected.

## What the game can detect

The browser exposes a controller ID, mapping type, button count, axes and values. A `standard` mapping means the browser has arranged a recognized layout; an empty mapping is an unknown/raw layout. It is unsafe to guess that raw axes or paddles are Xbox controls. [MDN mapping](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad/mapping), [MDN controller ID](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad/id).

Steam Input can present a virtual Xbox-compatible controller regardless of the physical device, or send keyboard/mouse events. The browser cannot reliably identify the underlying hardware or intercept Steam/KDE shortcuts that leave the game. Native Steam Input can provide physical button origins; this browser build does not use that API. [Valve gamepad-emulation guidance](https://partner.steamgames.com/doc/features/steam_controller/steam_input_gamepad_emulation_bestpractices).

## Current behavior

- New standard devices use browser-standard X (button 2) for bag work and Y (button 3) for boarding. When an actual legacy save exists, its actions migrate to the first recognized standard device. Existing custom actions remain. Earlier assumed X/Y names were not hardware evidence: unverified names now use standard positions, while explicit physical naming/verification is retained. A second new controller cannot inherit an unused legacy fallback after reload.
- Profiles are stored per browser-exposed ID, mapping and button/axis shape; switching devices restores their own gamepad bindings and names. Keyboard bindings remain shared. Two physical devices masked as an identical virtual controller cannot automatically receive different profiles.
- **Controller setup → Verify physical X / Y actions** asks for physical X, then Y and binds bag/descent and boarding accordingly. Helm controls are unchanged. **Name physical face buttons** only changes names. Standard/existing layout buttons offer explicit reversible presets; Controls / Remapping handles unusual axes/buttons.
- Unrecognized raw devices receive no guessed gameplay inputs. Menu/touch/keyboard controls and diagnostics remain available; map the needed actions explicitly or deliberately choose a known layout. Resting negative trigger axes are normalized so they do not jam the release gate.
- Prompts immediately follow actual keyboard/gamepad activity and the active profile. A keyboard-emulating Steam layout is displayed as keyboard input. The optional Steam keyboard label does not invent physical button mappings.
- Sticks and D-pad navigate according to the visible button layout, including horizontal chart utilities, crew portraits and berth slots. Up/Down wraps at vertical boundaries, including the selectable top-left Back; scrolling does not change the navigation order. LT/RT scrub forecasts while the working clock stays paused and cycle the search limit in orders; right stick scrolls detail panes. B and visible Back step through visited menus to title; Forward retraces them. Up from Continue selects Forward at title; within menus the arrow is next to Back and participates in directional focus. Explicit order/remapping/exit cancellation stays local. See [the clarified navigation amendment](docs/FEEDBACK_MENU_HISTORY.md). Resume/remapping/disconnect release gates prevent held controls leaking into the helm. Modified desktop key chords are not treated as boat commands; losing focus freezes simulation while preserving the current screen and draft.
- L3 opens chart tools; R3 opens difficulty / assists; B opens diver orders. Existing explicit custom mappings take priority. RB cycles Easy → Realistic → All Off in an Easy career, or Realistic → All Off in a Realistic career, retaining each mode's custom widget choices. Prototype reveal remains separate; Test Mode offers explicit reveal through training tools. Controls / Remapping shows one selected Keyboard, Controller or Steam Deck diagram beside dropdown choices and physical capture. [Keyboard amendment](docs/FEEDBACK_KEYBOARD_CONTROLS.md) preserves the controller mapping and Menu/B navigation.

## Highest-value physical check

Launch the existing shortcut through Steam with its **Gamepad** template and keep Steam running. Verify left-stick incremental throttle / lateral thrust exclusivity, right-stick horizontal rudder / vertical twin-jet neutral pivot (vertical scroll in menus), D-pad ahead/reverse/neutral, RT/LT zoom, L3 chart tools, R3 assists, B orders, LB diver selection, A nearby recall, then physical X bag-only/fresh descent and Y deployment/boarding. Run the two-button verifier if physical X/Y disagree with the prompts. Use only the controller through title → wharf → crew → departure → sea menu → Session Ended → B/Retry/Launcher.

Repeat with the built-in Deck pad in Desktop Mode. Use F4 / View diagnostics to compare browser device IDs, mapping, raw controls and focus. If a rear paddle exits to desktop, inspect its Steam/desktop action separately: the browser cannot suppress a shortcut it never receives. No global Steam/KDE layout or Flatpak permissions were changed by this pass.

Switch back to USB Xbox and test disconnect/reconnect. A synthetic controller test covers software routing, **not** these physical conditions.

## Startup enumeration diagnosis / launch-scoped remedy

A previous read-only host check found Valve mouse/keyboard interfaces and a Steam-created `Microsoft X-Box 360 pad 0`, with Linux axes `[0, 1, 2, 3, 4, 5, 16, 17]`. Those are kernel capabilities, not browser button numbers or proof of the correct per-game layout. `python3 scripts/controller-diagnostics.py` reads device metadata without changing Steam/drivers.

The installed Flatpak was identified as Firefox. Its Linux startup scan filters on udev `ID_INPUT_JOYSTICK`; hotplug receives device properties through the event. Read-only probes showed `/dev/input` readable while `/run/udev` was hidden. A scoped `/run/udev:ro` launch made both readable. The launcher now supplies that read-only path when launching Firefox Flatpak, alongside early gamepad/focus listeners and continuous fresh enumeration. Native Firefox remains supported. See [evidence and primary sources](docs/EXTERNAL_REFERENCES.md#firefox-cold-start-enumeration--2026-09-11). Personal/global browser and Steam settings remain unchanged.
